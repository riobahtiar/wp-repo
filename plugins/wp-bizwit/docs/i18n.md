# Internationalisation (i18n)

WP BizWit follows the official WordPress plugin i18n guide:

[How to Internationalize Your Plugin](https://developer.wordpress.org/plugins/internationalization/how-to-internationalize-your-plugin/)

## Rules (non-negotiable)

1. **Source language is English.** Every `__()` / `esc_html__()` / `esc_html_e()`
   string in PHP and every JS string via `resources/app/i18n.ts` uses an English
   *msgid*. Never put Bahasa Indonesia in the source string just because Indonesia
   is the primary market.
2. **Text domain is `wp-bizwit`.** Domain path `/languages` (plugin header).
3. **Indonesian ships complete** in `languages/wp-bizwit-id_ID.po` (+ compiled
   `.mo` / `.l10n.php` at release). An untranslated string is unfinished for this
   product.
4. **Switching the site language must switch the UI.** Set WordPress to
   English → full English chrome. Set to Bahasa Indonesia → full Indonesian.
   No mixed screens.
5. **Region ≠ language.** `Localization\Indonesia` still controls NPWP fields,
   rupiah formatting, and document rules when the UI is English. Field *labels*
   still go through gettext so the interface language wins for wording.

### Domain terms (OK in both languages)

These stay as Indonesian business terms in *both* locales (they are not “translated”
into invented English):

NPWP, NIB, NIK, PKP, PPN, PPh, SPK, BAST, SP2D, QRIS, UMKM, RT/RW, kelurahan,
kecamatan, satker, terbilang, bea meterai, kwitansi, faktur (when used as the
document name on paper).

Explanatory UI around them is still English in source and Indonesian in the catalogue.

## Files

| File | Role |
|------|------|
| `languages/wp-bizwit.pot` | Template (English msgids) |
| `languages/wp-bizwit-id_ID.po` | Indonesian translations (source of truth for translators) |
| `languages/wp-bizwit-id_ID.mo` | Binary for PHP (built; often gitignored) |
| `languages/wp-bizwit-id_ID.l10n.php` | PHP array loader (built) |
| `languages/*.json` | Script translations for `wp.i18n` (built when JS refs exist) |
| `src/I18n/Script_Strings.php` | Catalog so JS strings are extracted into the pot |
| `resources/app/i18n.ts` | Vue/TS bridge to `window.wp.i18n` |

## Workflow after adding strings

From monorepo root / package (use global `wp`, not Composer’s `vendor/bin/wp`):

```bash
cd plugins/wp-bizwit

# 1. Refresh template
$(command -v wp) i18n make-pot . languages/wp-bizwit.pot \
  --domain=wp-bizwit \
  --exclude=vendor,vendor-prefixed,node_modules,tests,bin,build

# 2. Merge into Indonesian catalogue
$(command -v wp) i18n update-po languages/wp-bizwit.pot languages/

# 3. Translate new msgids in languages/wp-bizwit-id_ID.po

# 4. Compile for runtime
$(command -v wp) i18n make-mo languages/
$(command -v wp) i18n make-php languages/
$(command -v wp) i18n make-json languages/ --no-purge
```

## How to verify both languages

```bash
# English UI
wp language core install en_US
wp site switch-language en_US
# Open BizWit screens — labels, buttons, notices in English

# Indonesian UI
wp language core install id_ID
wp site switch-language id_ID
# Same screens — Indonesian throughout; domain terms (NPWP, …) unchanged
```

Also load a project form, settings, and the dashboard Vue pilot: no leftover
opposite-language strings.

## Common mistakes

| Mistake | Result |
|---------|--------|
| Indonesian text as `__()` source | English site still shows Indonesian |
| Hardcoded text in Vue without `i18n.ts` | Never translates |
| Forgetting `wp-i18n` script dependency | JS falls back to English only |
| Forgetting `wp_set_script_translations` | JS never loads `.json` translations |
| Translating domain terms into awkward English | Confuses Indonesian users reading English UI |

## PHP vs region

```php
// GOOD — English source, translated via catalogue
__( 'Budget', 'wp-bizwit' );

// GOOD — region may override the label, still gettext under the hood
$region->field_label( 'budget', __( 'Budget', 'wp-bizwit' ) );

// BAD — Indonesian source
__( 'Anggaran', 'wp-bizwit' );
```
